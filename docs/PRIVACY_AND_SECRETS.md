# Privacy and Secrets — Mandatory Requirement

*Version 1.0 — May 2026*
*Status: MANDATORY — no bypass, no exceptions*

---

## Governing Principle

> **Stallone must never store sensitive information in plaintext anywhere in the application or database — not in task descriptions, learnings, memory artifacts, logs, or any other persistence layer. This is a hard architectural constraint, not a best-effort guideline.**

This applies to every project Stallone builds for itself and for users. If a piece of data is sensitive, it is either encrypted at rest or it is not stored.

---

## What Counts as Sensitive

Any data matching one or more of the following:

| Category | Examples |
|---|---|
| API keys / tokens | `ghp_*`, `AIza*`, `sk-*`, `Bearer <token>`, Railway tokens, Telegram bot tokens |
| Credentials | Passwords, database connection strings with passwords, SSH private keys, PEM blocks |
| PII | Names, emails, phone numbers, physical addresses |
| Absolute file paths | Paths containing OS usernames (e.g. `/Users/aritrarpal/...`) |
| Raw shell output | `env` dumps, process output that may contain any of the above |
| LLM prompt/response fragments | When they contain any of the above categories |

---

## Mandatory Controls — By Layer

### 1. Ingress Scrubbing (before any DB write)

A `scrubSensitive(text)` function MUST be applied to every string before it is written to the database. This includes:

- Task `title`, `description`
- Learning `observation`, `keywords`
- Memory artifact `content`
- Step logs (`step_logs` table or equivalent)
- Repair state fields (`lastFailureMessage`, `lastOutcome`)
- Verification summaries
- Any LLM-generated text persisted to DB

**Pattern-based redaction** (minimum required patterns):

```
ghp_[A-Za-z0-9]{36,}          → [REDACTED:github-token]
AIza[A-Za-z0-9\-_]{35}        → [REDACTED:google-api-key]
sk-[A-Za-z0-9]{32,}            → [REDACTED:openai-key]
Bearer\s+[A-Za-z0-9\-._~+/]+=* → [REDACTED:bearer-token]
-----BEGIN [A-Z ]+KEY-----.*?-----END [A-Z ]+KEY----- → [REDACTED:pem-block]
postgresql://[^@]+@             → postgresql://[REDACTED]@
/Users/[^/\s]+                  → /Users/[REDACTED]
/home/[^/\s]+                   → /home/[REDACTED]
```

Patterns run in order; each match is replaced, not dropped. The scrubbed text is what gets stored.

### 2. Encryption at Rest — DB Fields

The following columns MUST store their values encrypted (AES-256-GCM) if they could ever contain sensitive data by design:

| Table | Column(s) | Reason |
|---|---|---|
| `tasks` | `description` | User-supplied; may contain tokens, paths |
| `memory_artifacts` | `content` | LLM-generated; may reflect task input |
| `learnings` | `observation` | Derived from task; may contain failure output |
| `step_logs` | `output` | Raw shell output; high risk |
| `skills` | `template` | Generated from task patterns |

Encryption key: loaded from env var `STALLONE_ENCRYPTION_KEY` (32-byte hex). Never stored in DB. If the key is missing, Stallone MUST refuse to start.

Decryption happens in the application layer only — never in SQL queries. The DB stores ciphertext blobs; the application decrypts before use.

### 3. Log Sanitization

The pino logger MUST have a `redact` configuration covering at minimum:

```js
redact: [
  'req.headers.authorization',
  'req.headers["x-control-token"]',
  '*.apiKey',
  '*.token',
  '*.password',
  '*.secret',
  '*.connectionString',
]
```

Additionally, before logging any LLM prompt or tool output longer than 500 characters, pass it through `scrubSensitive()`.

### 4. Skill and RAG Corpus

- Skills generated by `skillGenerator.js` MUST have their `template` field scrubbed before storage.
- RAG-ingested documents MUST be scanned for secrets before chunking. Any chunk containing a match for the ingress scrubbing patterns is dropped entirely (not stored).

### 5. Gemini / Ollama Prompt Hygiene

Before sending any text to an external LLM (Gemini API), Stallone MUST scrub the prompt for secrets. This prevents accidental exfiltration of credentials to third-party APIs even if they somehow entered the system.

This applies to:
- Task context injected into Gemini prompts
- Retrieved memory artifacts and learnings
- RAG chunks

### 6. No Sensitive Data in Error Messages

When returning errors via the Control API (`/v1/*` endpoints), error messages MUST be sanitized. Raw DB errors, stack traces with file paths, and LLM error responses MUST NOT be returned to API callers verbatim.

---

## Enforcement — Startup Gate

`src/config.js` MUST validate:

```js
STALLONE_ENCRYPTION_KEY: z.string().regex(/^[0-9a-f]{64}$/i, 'Must be a 64-char hex string (32 bytes)')
```

If missing or malformed: **hard crash on boot**. No graceful degradation. This is intentional — running without encryption is worse than not running.

## Implementation Plan

### Phase A — Ingress Scrubbing (no DB migration needed)
1. Create `src/privacy/scrub.js` — exports `scrubSensitive(text): string`
2. Wire into `learnings/extractor.js` before DB insert
3. Wire into `memory/exactArtifacts.js` before DB insert
4. Wire into `control/api.js` error responses

### Phase B — Encryption at Rest (requires DB migration)
1. Add `STALLONE_ENCRYPTION_KEY` to `src/config.js` schema (required)
2. Create `src/privacy/encrypt.js` — AES-256-GCM encrypt/decrypt using the env key
3. DB migration: add `_encrypted` boolean flag column alongside each target column, or use a naming convention (`description_enc`)
4. Wrap DB reads/writes for target columns in encrypt/decrypt transparently
5. One-time migration script to encrypt existing plaintext rows

### Phase C — Log Redaction
1. Add `redact` array to pino config in `src/index.js`
2. Add pre-log scrubbing for long strings in the logger wrapper

### Phase D — Gemini Prompt Hygiene
1. Wrap `geminiDriver.js` `callGemini()` to scrub context before sending
2. Unit test: inject a fake API key into context, assert it is redacted in the outbound prompt

---

## Non-Negotiables

- `scrubSensitive()` has **no override flag**. There is no `{ skipScrub: true }` option.
- Encryption key rotation requires a migration script — it is not a runtime toggle.
- The `STALLONE_ENCRYPTION_KEY` env var is never logged, never echoed in health endpoints, never returned by the Control API.
- PRs or tasks that attempt to bypass these controls MUST be rejected by the Gemini review loop (add a review rule: "reject any change that removes scrubSensitive calls or skips encryption").

---

## Open Questions (to resolve before Phase B implementation)

1. **Searchability vs. encryption trade-off** — encrypted `learnings.observation` can't be keyword-searched in SQL. Options: (a) store keywords unencrypted, encrypt only full observation text; (b) move keyword search to application layer after decrypt; (c) use a search index on decrypted content at query time. **Recommended: option (a)** — keywords are already low-sensitivity (single words), observations are where the risk lives.

2. **Existing data** — all rows in `tasks`, `learnings`, `memory_artifacts` written before Phase B are plaintext. The migration script must encrypt them in a single transaction per table, with a rollback path.

3. **Ollama (local) vs. Gemini (remote)** — Gemini prompt hygiene (Phase D) is the higher priority since Gemini calls leave the machine. Ollama is local, so the risk is lower, but scrubbing still applies for consistency.
